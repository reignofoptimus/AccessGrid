# Deploy AccessGrid to Render

The UI is unchanged. The backend uses a bundled ONNX version of the original trained model, CPU-only ONNX Runtime and Tesseract. PyTorch/Ultralytics are used only when re-exporting the model, not in the production image.

## 1. Create a persistent PostgreSQL database

Use a PostgreSQL provider and retain its connection URL privately. Render's free PostgreSQL is suitable for an initial test but expires after 30 days; choose a database arrangement that lasts as long as your resume link. External PostgreSQL connections should use the provider's required TLS settings, typically `?sslmode=require`. SQLite is not used for hosted records or rate-limit counters.

## 2. Deploy the backend

Push this version to GitHub. In Render, choose **New â†’ Blueprint**, connect the AccessGrid repository, and use its root `render.yaml`. This defines one free Docker web service; it does not create paid resources or a database.

Supply these environment variables in Render:

| Variable | Value |
|---|---|
| `DATABASE_URL` | Your private PostgreSQL connection URL. Both `postgres://` and `postgresql://` are supported. |
| `BOOTSTRAP_ADMIN_USERNAME` | Your chosen username, 3â€“64 letters, digits, underscores, dots or hyphens. |
| `BOOTSTRAP_ADMIN_PASSWORD` | A unique password of 12â€“128 characters. Do not put it in source or screenshots. |
| `SECRET_KEY` | Generated by the Blueprint; keep it stable across deployments. |
| `ACCESSGRID_PRODUCTION` | `1`, already set by the Blueprint. |
| `CORS_ORIGINS` | Your exact Vercel frontend origin, or leave empty when exclusively using the same-origin proxy below. Never `*`. |

For manual service creation instead of a Blueprint: select Docker, Dockerfile path `backend/Dockerfile`, Docker build context `backend`, leave the service root directory empty, select Free, and set health-check path `/healthz`. Leave the Docker command override empty. The image uses `$PORT` automatically.

Startup applies migrations under a PostgreSQL advisory lock, creates the initial administrator if absent, initializes four empty parking zones and starts one Gunicorn worker. It never clears vehicles, users, visits or zone occupancy. Existing accounts/passwords are never overwritten. Remove `BOOTSTRAP_ADMIN_PASSWORD` after the first successful deployment if desired; an existing administrator allows subsequent startups without it. To create additional accounts, use the authenticated administrator-only `/api/auth/register` endpoint; no public sign-up grants roles.

The model is loaded and warmed in the worker before it serves traffic. `/healthz` checks the database; `/readyz` additionally confirms the detector/Tesseract availability. A missing model or executable fails startup rather than pretending recognition worked. Wait for Render to report **Live**, then open `/readyz` and expect `{"status":"ok"}`.

## 3. Connect the Vercel frontend

After Render assigns the service's actual HTTPS address, run from the repository root:

```sh
python backend/tools/configure_frontend.py --backend-url https://YOUR-ACTUAL-SERVICE.onrender.com
```

Commit the generated `frontend/vercel.json`. Import the same repository into Vercel with root directory `frontend`, framework Vite, build command `npm run build` and output directory `dist`. Leave `VITE_API_URL` unset. Requests to `/api/*` then proxy to Render through Vercel; the existing HttpOnly/SameSite=Lax session cookie remains first-party. There is no UI redesign or browser-exposed backend secret.

The client request timeout is now 120 seconds to accommodate a sleeping Render service. Gate operations are never automatically retried after an ambiguous timeout.

Direct cross-site browser requests to the Render URL are an alternative only after explicitly configuring `SESSION_COOKIE_SAMESITE=None`, secure cookies and exact `CORS_ORIGINS`; browser third-party-cookie restrictions can still interfere. The same-origin proxy is the supported setup.

## 4. Verify the hosted app

Sign in with the private bootstrap account, register a sample vehicle, record entry/exit, and upload a clear consented plate photo. Confirm that records survive a restart. Test the first visit after the service sleeps. ANPR requires an authenticated admin/security account, real JPEG/PNG content, and remains rate limited. Busy recognition returns 429; unavailable recognition returns 503; an OCR deadline returns 504. No detected/readable plate returns `plate: null`.

For a resume, give recruiters a limited sample-data account rather than your private administrator password. Browser `?demo` shortcuts remain development-only. Do not run `seed.py` on the hosted database.

## Resource bounds and verification

- One worker, two HTTP threads, one recognition at a time. ONNX/OpenCV use one CPU thread; no CUDA/PyTorch serving dependencies.
- Uploads limited to 8 MB and 12 million pixels, downsampled to at most 1600Ã—1600 before detector conversion. Model input stays 640Ã—640. OCR crops never exceed 960Ã—256 and Tesseract has a five-second deadline.
- Model export was compared with original PyTorch predictions on zero/random tensors (maximum absolute difference below 0.00043). This validates export numerics, not real-image recognition accuracy.
- Fresh production-environment installation and Linux wheel availability were checked; backend unit/security tests pass. Windows model-inference probe peaked at about 214 MiB, excluding the OCR subprocess and live database pool.
- `.github/workflows/render-backend.yml` builds the actual Linux Docker image, starts PostgreSQL, runs the app under a 512 MB cgroup cap and tests real ONNX inference and Tesseract OCR. The Linux validation passed: [Render backend run 44113030813](https://github.com/reignofoptimus/AccessGrid/actions/runs/44113030813). PostgreSQL startup/login, actual ONNX HTTP inference, actual Tesseract OCR, repeatable initialization and all 27 tests succeeded under the 512 MB cap, with no OOM kill. The final steady memory snapshot was about 199 MiB (not a peak measurement or a concurrent-load guarantee).

## Re-exporting the trained model

The checked-in `backend/app/anpr/best.onnx` is derived from `best.pt`; `model-metadata.json` records source/export hashes and parity results. To regenerate, use a separate environment containing CPU PyTorch, Ultralytics 8.4.21, ONNX and ONNX Runtime, then run `python backend/tools/export_model.py` and `python backend/tools/verify_model.py`. Export uses fixed 640 input, opset 17, no dynamic dimensions and no embedded NMS. Preserve this contract unless the decoder is updated too. Do not run model export on Render startup.
